The repo is layered top-to-bottom and **dependencies only point downward**. A
package's name encodes its layer (`@r10c/<area>-<lang>-<name>`) — except the
framework, whose packages are `@entifix/<name>`, named for what they are rather
than where they sit because they are published
([ADR 0059](../adr/0059-entifix-leaves-the-repo.md)) — and the Nx
ESLint rule `@nx/enforce-module-boundaries` **fails the build** on any upward edge.

```
apps/                               ← runtime hosts (Next.js frontends / Effect-native services)
packages/shells/next/*              ← per-domain shells: a domain mounted onto the framework's Next shell
packages/shells/effect/*            ← per-slice shells: a slice's cells, consumers and sweeps composed onto the fleet base
packages/implementation/<key>/<tech> ← cells: one domain (or store) written in one technology
packages/business/ts/<domain>       ← pure domain entities & use-cases (no framework)
packages/utils/ts/*                 ← generic TS helpers
@entifix/*  (installed)             ← the framework: entity system, adapters, UI and base shells
```

The boundary is enforced by the tag dimensions declared in every project's
`package.json` `nx.tags` (see `eslint.config.mjs`):

- **`layer:*`** — `app` › `shell` › `implementation` › `business` › `utils`; a project may depend only on layers **below** it. `shell` and `business` additionally allow same-layer edges, which their own dimension below then orders. The framework is **not** a layer here: `@entifix/*` is installed from the registry, an external package carries no tags, and any project may import it — what orders the framework internally is its own `tier:*` contract, below.
  One project sits beside the ladder rather than on it: **`layer:docs`**, the documentation site (`apps/docs-site`). It runs nothing and exports files, and it may depend only on `contract:register`, `business` and `utils` — so it reads the registers no `layer:app` may import, and nothing else.
- **`contract:register`** — the two registers that **are** the contract (ADR 0025, [ADR 0080](../adr/0080-a-capability-register-holds-one-thin-entry-per-use-case.md) §7): `tools/capabilities/` and `tools/slices/`. Both are also `type:testing`; this tag is what lets the docs site read them without opening `type:testing` to a shipped project.
- **`scope:*`** — a domain scope (`marketplace`, `marketplace-admin`, `auth`, `config`, `transaction`, `realtime`, `stock`, `order`, `payment`, `settlement`, `sales`, `fulfilment`) may depend only on itself or `scope:shared`; the host scope `back-office` may also reach the domain scopes it mounts (`eslint.config.mjs` is the list), and the host scope `docs` — carried only by `tools/docs-reference`, which writes each service's OpenAPI document and the composed flows for the documentation site — may reach every domain scope, because the site itself is `layer:docs` and imports no shell; `scope:shared` (all of `business` and `utils`) is the reusable core, dependable by anyone. An implementation cell carries the scope of the slice that owns its domain, never `scope:shared` — a second host reaches it by widening the **host** scope, as `scope:back-office` does.
- **`business:*`** — internal ordering inside the business layer: `vocabulary` ‹ `policy` ‹ `domain`. `business:vocabulary` is pure values with no r10c dependency — `sales-vocabulary`'s sale units, scales and `lineTotal` — which a contract has to name as much as a domain does ([ADR 0082](../adr/0082-an-offering-is-sold-in-a-unit-with-a-step.md)). `business:policy` is the shared language any domain may express itself in — r10c's grant table (`authz-grants`), the catalog, order, payment and flow contracts — beside the installed `@entifix/authz` it builds on, and it may reach down to the vocabulary; a `business:domain` package may reach down to both but **never sideways to another domain**.
- **`tech:*`** — what an implementation cell is **written in**: `react`, `next` and `http` cells are keyed by domain, `mongo`, `redis` and `sql` cells by store ([ADR 0060](../adr/0060-the-implementation-layer-cells.md)). Every implementation project carries exactly one, and `@r10c/docs-check` fails one that carries none or two. It decides what the cell may not **talk through**, as a `bannedExternalImports` rule:
  - a `react`, `next` or `http` cell may not import an adapter (`@entifix/{rest,static,mongo,sql,redis,amqp,jwt,zitadel,posthog}`), a driver, `@entifix/react-controls/i18next`, `@entifix/next-shell/server`, `@tanstack/*` or redux — those are chosen at composition, by a shell or an app; a `react` cell also may not import `next`, and an `http` cell nothing that renders or serves (`effect/http*`, `@entifix/service-shell`) — it declares, its shell serves ([ADR 0071](../adr/0071-http-cells-hold-descriptors-and-the-slice-shell-builds-the-api.md));
  - a `mongo`, `redis` or `sql` cell **is** the adapter, so it may import its own engine's entifix client and driver — and nothing for UI or HTTP, and no other engine's.
  - an `smtp` cell is the same shape for a transport rather than a store: it may import its driver (`nodemailer`) and nothing for UI, HTTP or any engine, and no engine cell may import `nodemailer`. order-management's is the one that mails a storefront buyer (ADR 0076 §6).
  - an `fs` or `gcs` cell is an object store's adapter — a directory in the lab, a Cloud Storage bucket in the cloud — the same shape again: its own driver (`node:fs` or `@google-cloud/storage`) and nothing for UI, HTTP or any other engine, and no other cell may import `@google-cloud/storage`. A Node builtin is not an external import to the boundary rule, so `node:fs` is banned nowhere. The payment-evidence store's pair keeps payment receipts (ADR 0081 §8).

  Cell→cell is illegal without a rule of its own: `layer:implementation` allows no same-layer edge. A need that crosses domains goes through a `business:policy` contract or is composed by the shell, which is why the storefront's category page resolves a slug through `catalog-reference/next` and then filters `marketplace-catalog/next` by the id. `@r10c/conventions` lints a planted cell→adapter import and fails if the ban stops catching it.
  The same ban covers `@entifix/workflow` and the mechanism halves entifix keeps at their own subpaths — `@entifix/transactions/engine`, `@entifix/service-shell/{runtime,observability,testing,push,push/sse}` and `@entifix/react-integration/event-source` — so a cell writes against `.` and composition picks the engine.

- **`shell:*`** — `shell:base` is `@r10c/shells-effect-service`, the fleet composition every Effect service shares. `shell:domain` marks one slice's shell that owns a domain — a Next shell, or a slice's Effect shell — and `shell:platform` one whose slice declares none (`transaction`, `realtime`). Both mount onto the base (and onto the installed `@entifix/service-shell`, `@entifix/next-shell`, `@entifix/next-i18n`, reachable without a tag) and **never import another shell**; the base imports neither ([ADR 0064](../adr/0064-failures-reach-the-slice-shell.md)).
- **`tier:*`** — entifix's own composition contract, carried only by the packages it publishes and checked in the entifix repository by `pnpm nx test @entifix/tiers` rather than by the boundary rule here. Six tiers — `0` standalone (`style`, `tooling`) ‹ `1` entity (`core`, `business`) ‹ `2` adapters (the datastore, REST, JWT, Zitadel and PostHog clients, plus `transactions` and `i18n` — the i18next binding is an adapter to an external library exactly as a driver binding is, which is why it is not standalone) ‹ `3` ui (`react-controls`, `react-integration`) ‹ `4` app framework (the authorization vocabulary and the three base shells) ‹ `5` testing — and a package may depend on its own tier or below.
  ⚠️ **The rule that matters is not the direction.** A hard dependency on a capability the tier is meant to be adoptable without fails the build even though it points downward: a table must not arrive with i18next attached, a Mongo repository must not arrive with the saga engine, and Playwright session helpers must not arrive with three database drivers. Those edges belong in `peerDependencies` with `peerDependenciesMeta.optional`, behind a subpath export — package-level dependencies are not per-subpath, so the optional peer is the part that does the work. The register is entifix's `tools/tiers/src/registry.ts` and
  [ADR 0059](../adr/0059-entifix-leaves-the-repo.md) is the reasoning.
- **`host:*`** — `host:next` (a Next app) may **not** import entifix's datastore clients (`@entifix/mongo`, `@entifix/sql`, `@entifix/redis`, `@entifix/amqp`, or any subpath of them) or the durable flow engine (`@entifix/workflow`) — a `bannedExternalImports` rule, because an installed package carries no tag to match. A Next backend is composition — cookies, proxying, RSC aggregation — never data access; only a `host:effect` service binds a repository to a datastore.

Spec files may additionally import `type:testing` libs (doubles/fixtures); source files may not. **To add a queryable/importable edge, retag the project — never weaken the rule.** The value of the layering is substitutability: a `business` use-case depends only on contracts (`@entifix/business`), so the same use-case runs on the web against a REST adapter and on a backend against a Mongo adapter, the transport injected at the composition root.
