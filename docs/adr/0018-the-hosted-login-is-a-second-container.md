# 18. The hosted login is a second container

- Status: Accepted
- Date: 2026-08-08

## Context

[ADR 0016](0016-zitadel-authenticates-r10c-authorizes.md) moved authentication to
Zitadel's hosted login. Which hosted login was never recorded as a decision — it
was a line in a seed script.

Zitadel v4 rewrote the login as **v2**, a standalone Next.js application shipped
as its own image (`ghcr.io/zitadel/zitadel-login`), and defaults the instance
feature `loginV2.required` to `true`. The core image serves nothing under
`/ui/v2/login`, so an instance left at that default answers **404** on every
authorization redirect while `/debug/ready` stays green — a broken sign-in button
behind a healthy fleet, which is exactly the failure a health ladder cannot see.

`tools/zitadel-seed.mjs` therefore wrote `loginV2.required = false`, pinning the
lab to the v1 login the core still serves. That bought a working sign-in for one
fewer container, and it was the right call at the time: v1 serves password, TOTP,
social providers and self-registration, which is everything this lab exercises.

But the pin was a deprecation clock, not a decision (issue #51). Three things
would make it come due: Zitadel announcing a removal version for v1, something
the lab needs landing only in v2, or wanting the hosted login to look like r10c.
The third is the one that fired. The hosted login is the only screen in the fleet
that ignores `@r10c/entifix-style`, and v2 is themable in ways v1 is not. Doing
the move now means doing it without a 404 setting the schedule.

## Decision

Run the v2 login container in the local lab, and let Zitadel require it.

### It gets its own origin, not a path on Zitadel's

`infra/local/zitadel-login` is a Deployment plus a NodePort **Service on 30081**.
The instance's `loginV2.baseUri` is `http://localhost:30081/ui/v2/login/`.

Upstream's compose puts the core and the login behind one domain with Traefik,
path-routing `/ui/v2/login`. That is the right shape for a real deployment and
the wrong one here: it would add a reverse-proxy workload to the lab, a rung to
the ladder, and h2c passthrough for Zitadel's gRPC — to buy a single origin we do
not need. Dev cookies are host-scoped and `localhost` shares them across ports,
which is already why one redirect URI covers the whole fleet.

The login reaches the core in-cluster at `http://zitadel:8080`, with
`CUSTOM_REQUEST_HEADERS=Host:localhost`. Zitadel resolves which instance a
request belongs to from the Host header, and `zitadel` is not one of the
instance's domains; without the override every API call answers
`Errors.Instance.NotFound`. That override was itself broken in login `v4.14.0`
and fixed before the pinned tag ([zitadel#12125](https://github.com/zitadel/zitadel/issues/12125)),
which is one more reason the image is pinned and moves with the core's.

### The token comes from first-instance init, so this needs a reset

The login authenticates to the core's session API as a machine user holding
`IAM_LOGIN_CLIENT`. Zitadel creates that user and writes its PAT when it creates
the instance — `ZITADEL_FIRSTINSTANCE_ORG_LOGINCLIENT_*` on the core deployment,
landing in the same `machinekey` emptyDir the seed's PAT already uses, read out
through the same `pat-reader` sidecar (the Zitadel image is distroless and has no
`cat`).

`FIRSTINSTANCE_*` keys fire only when the instance is created. An instance that
predates this change never grows the user, and there is no in-place upgrade path
— **this change requires one `pnpm run <app>:dev:reset`**. That is the sanctioned
migration in this repo, not a workaround: nothing runs in production, and a
compatibility path for a dev lab is dead code with a maintenance cost. What the
ladder owes the operator is to say so, which is why the extraction failure names
both causes (a pod that restarted after init, and an instance older than the
setting) and points at reset.

The PAT reaches the pod as `zitadel-login-secret`, applied imperatively by the
ladder rather than generated by kustomize, because its value does not exist until
the core has booted.

### The login comes up before the flag flips

The ladder gains a rung, and the seed moves down one:

```
L6 hosted login   secret + apply -k + rollout + /ui/v2/login/healthy
L7 zitadel seed   project, OIDC app, loginV2 + baseUri, policy, SMTP, IdP
```

That order is the point. L7 is what sets `loginV2.required = true`; running it
first would flip the instance towards an address serving nothing, and a failure
between the two rungs would leave precisely the green-probes-404-sign-in state
the v1 pin existed to avoid. `ensure.sh`'s fast path asks `login_ready` too, so a
login container that dies later is not reported as a healthy fleet.

`zitadel-login` is deliberately absent from `PLATFORMS`: that list is applied at
L3, long before the token exists.

## Consequences

- **`ZITADEL_SEED_REVISION` is 3.** Rev 2 → 3 turns login v2 on and sets its base
  URI. The rule from [ADR 0017](0017-back-channel-logout-from-the-identity-provider.md)
  holds: bump it in the same commit as any seed change that adds or alters an
  instance setting, or the change reaches only machines that happened to reset.
- **`ensureLoginV2` reconciles on `baseUri`, not just on `required`.** An instance
  seeded before the address moved would otherwise keep the old one forever — the
  same trap `ensureApp` fell into with `backChannelLogoutUri`.
- **No r10c TypeScript changed.** `oidc-client.ts` builds every URL from the
  discovery document, and the hop to the login is a redirect Zitadel performs
  internally. The login version is invisible above the OIDC boundary, which is
  the property that made this an infrastructure change rather than a client one.
- **The e2e login fixture is route-keyed now.** `seedSession`'s step machine used
  v1's `loginName`/`password` field names, its "Skip" button and its "Other User"
  link. v2 gives each step its own route under `/ui/v2/login` and reuses its
  `data-testid`s across screens (`reset-button` is "Reset password" on one screen
  and "Skip" on another), so the machine switches on the pathname —
  `/loginname`, `/password`, `/mfa/set`, `/accounts` — and uses testids only
  within a route it has already identified.
- **A second image tag must move with the core's.** The login is a client of the
  core's session API, not an independent product. Today that agreement is two
  literals in two manifests with nothing enforcing it (issue #59).
- **Port 30081 joins the required set, which costs a cluster recreate.** A fleet
  whose login is unreachable cannot obtain a session — a stopped fleet rather
  than a degraded one, the same weight 30080 already carries. A minikube cluster
  is created with its `--ports` mapping and cannot grow one, so an existing
  cluster fails L2 with `NodePorts not published: 30081` until
  `bash infra/local/reset.sh --hard` recreates it. The ladder says exactly that;
  it is the same answer any new NodePort has always had.
- **The Google IdP's authorised redirect URI moves.** It is registered against
  the core, not the login, so it is not `:30081` — but it is no longer v1's
  `/ui/login/login/externalidp/callback` either. `infra/local/zitadel/.env.example`
  carries the current value.
- **This supersedes the `ensureLoginVersion` reasoning in ADR 0016's
  local-development consequence.** Everything else in ADR 0016 stands: Zitadel
  still authenticates, r10c still authorizes, and r10c still holds no credential.
