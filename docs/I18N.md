# Internationalization

The fleet ships **`es` (default) and `en`**. i18n is structural, not a
convention: a user-facing string written straight into JSX fails lint, a
misspelled key fails to compile, and a catalog that drifts fails CI.

The reasoning behind every choice here lives in
[ADR 0003](adr/0003-i18n-mandatory.md).

## The pieces

| Where                                       | What it owns                                                                                              |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `@r10c/entifix-ts-i18n`                     | Locales, negotiation, `Intl` formatters, the i18next instance factory, `getServerTFor`, **all catalogs**. |
| `@r10c/entifix-ts-i18n/routing`             | Locale type + negotiation only. Edge-safe: no i18next, no catalogs.                                       |
| `@r10c/entifix-react-controls` → `src/i18n` | `I18nProvider`, `useT`, `useFormatters`, `useLocale`, `useTranslateKey`, `useErrorMessage`.               |
| `@r10c/shells-next-i18n`                    | `resolveLocale` / `rewriteToLocale` / `rememberLocale` (edge middleware).                                 |
| `@r10c/shells-next-i18n/server`             | `getRequestLocale`, `getServerT`, `getServerTranslateKey`; re-exports `getServerTFor`.                    |
| `@r10c/shells-next-common` (client barrel)  | `LocaleLink`, `useLocaleHref`, `usePathLocale`.                                                           |

## Namespaces

One per owner, all under `packages/entifix/ts/i18n/src/resources/{es,en}/`:

- **`controls`** — the agnostic entity UI (table, form, filters, sorting, validation).
- **`shell`** — Next back-office chrome and the tab workspace.
- **`errors`** — the code vocabulary services answer with.
- **`entity`** — entity and member labels, keyed by the entity's own `@entity({ key })`.
- **`app`** — per-app copy, one sub-tree per app.

`es` is the source of truth. The `en` files are annotated `typeof import('../es/…')`,
so a key present in Spanish and missing in English **does not compile**.

## Routing

Locale lives in the URL as a path prefix, always. **How a page then reads it
differs by app, and the difference decides whether that app can be
prerendered.**

### The back-offices: rewrite + header

back-office-app has no `app/[locale]` segment. Middleware
redirects an unprefixed path to `/<locale>/…`, then rewrites the prefixed one
back onto the plain route tree with an `x-r10c-locale` header.

```ts
// apps/<name>-app/src/middleware.ts — from '@r10c/shells-next-i18n'
const locale = resolveLocale(request);
if (locale.redirect) return locale.redirect; // nothing to authorize about a URL they're leaving
// … your own gates, matching on `locale.pathname` (the stripped path) …
return rewriteToLocale(request, locale);
```

Pages read it with `getRequestLocale()` / `getServerT()`. Both call `headers()`,
which is a **dynamic request input** — so every page that renders copy is
server-rendered on demand. For an auth-gated app whose every response is
personal that costs nothing, and it saves threading a `locale` param through
every page in three apps.

### The storefront: a real `[locale]` segment

marketplace-app is public and read-heavy, so the same trade is the wrong one:
`headers()` would make prerendering impossible. It carries `app/[locale]/…`
instead, its middleware **only redirects** (no rewrite, and no `Set-Cookie` on
the pass-through, which would stop a shared cache serving a static page), and
pages read `params.locale` and bind copy with **`getServerTFor(locale, ns)`**.

That binder reads nothing about the request, so `generateStaticParams` can emit
one prerendered copy per locale. It lives in `@r10c/entifix-ts-i18n` rather than
the Next i18n shell because `layer:shell` forbids same-layer edges and the
storefront shell needs it; `@r10c/shells-next-i18n/server` re-exports it so app
call sites keep both binders in one import.

Precedence: path prefix › `r10c_locale` cookie › `Accept-Language` › `es`.

**Every internal href carries the prefix.** In the back-offices that means
`LocaleLink` / `useLocaleHref()` from `@r10c/shells-next-common`, which read the
locale from context and are therefore client components. The storefront has the
locale as a route param, so it uses its own **server** `StoreLink` and pays no
client JS for a link. All of them are idempotent and leave absolute URLs alone,
so applying them blindly is safe.

### The one screen that is not ours: `ui_locales`

Sign-in happens at Zitadel's hosted login, which no gate below can reach — it is
a different application, and a visitor reading Spanish who is handed an English
sign-in screen and back is an inconsistency nothing in this document would catch.
So the locale is **stated on the authorization request**: the shell's
`/api/auth/oidc/start` reads the `r10c_locale` cookie (the middleware skips
`/api` wholesale, so there is no locale header on that request), auth-service
checks it with `isLocale` and passes it to `authorizationUrl`, which sets
`ui_locales`.

The check belongs to **auth-service**, not to the app in front of it: the value
starts life in a cookie the browser controls and ends up in a URL the provider
renders, and the service answers on `:3102` where anything can call it. An
unrecognised tag is dropped rather than echoed, and a request that states no
locale sends no parameter at all — which leaves Zitadel negotiating from
`Accept-Language`, exactly as before.

## Writing copy

```tsx
const t = useT('app'); // namespace-bound; `t('errors:x')` will NOT typecheck
return <Button>{t('auth.submit.signIn')}</Button>;
```

Need a second namespace in one component? Bind it separately —
`const errorT = useT('errors')`. In a server component use
`await getServerT('app')` — or, on a route with a `[locale]` segment,
`getServerTFor(locale, 'app')`, which is synchronous because it reads nothing
about the request.

Interpolation is i18next's: `t('controls:validation.required', { field })`.
Word order differs between locales, so **never** concatenate a label with a
suffix — put the whole sentence in the catalog with a placeholder.

### Runtime keys

A key that is only known at runtime — an entity's `labelKey`, a nav label held
in a route table — cannot satisfy the typed signature. Two escape hatches exist,
and they are the _only_ two:

- `useTranslateKey()` (client)
- `getServerTranslateKey(ns)` (server)

Authored copy must keep going through `useT` / `getServerT` so a typo stays a
compile error.

## Entities

Labels are keys carried in metadata and resolved in the browser — resolved copy
never crosses the wire. Column descriptors are read client-side from the shared
entity class; **use-case** descriptors are served by
`GET /api/<entity>/$metadata`, because an action's availability depends on the
caller ([ADR 0026](adr/0026-the-use-case-descriptor-and-served-entity-metadata.md)).
That document carries keys too, so nothing about resolution changes.

```ts
@entity({
  domain: 'product-configuration-management',
  key: 'product',
  labelKey: 'entity:product.label',
  pluralKey: 'entity:product.plural',
})
class Product {
  @accessor({ type: 'string', label: 'Code', labelKey: 'entity:product.fields.code' })
  get code() { … }

  @accessor({
    type: 'enum',
    labelKey: 'entity:user-identity.fields.role',
    enumValues: Roles,
    enumLabelKey: 'entity:user-identity.values.role', // value → `${prefix}.${value}`
  })
  get role() { … }
}
```

`label` stays as the untranslated fallback, so a member with no catalog entry
still renders something. `describeEntityColumns` carries `labelKey` and never
resolves it — the same descriptors are the **server-side filter allowlist**,
where a translated label would be meaningless. Resolution happens in
`useLocalizedDescriptors` / `useEnumLabel`.

## Errors

Services answer a failure with `{ error, code, detail }`:

- `error` — English, for logs and for consumers that do not know the vocabulary.
- `code` — a key in the `errors` catalog. **This is what the user reads.**
- `detail` — diagnostic; never rendered.

The rest client lifts `code` onto `EntifixError.details`, and `useErrorMessage()`
translates it, falling back to `message`. Adding a failure reason means adding a
code to `errors` and answering with it — not writing a sentence in a route.

**Answering with a code that has no entry is a build failure**, and it has to be,
because nothing else can see it: `useErrorMessage` translates through
`useTranslateKey`, whose cast discards the typed-key augmentation, and a code
missing from both locales is symmetric so `check-i18n.mjs` reads it as fine. The
user sees the identifier — `noActiveOrganization` — in the error slot.
`@r10c/i18n-check` scans `apps/` and `packages/` for the two shapes a code is
emitted in, the `{ error, code }` body literal and the second argument of a
`CodedAuthnError` subclass, and fails on any that the catalog lacks. The reverse
is deliberately not checked: `network`, `configUnavailable` and `unexpected` are
synthesized in the browser and have no emission site to find.

## Formatting

Never call `toLocaleString()` / `toLocaleDateString()` without a locale: the
server and the browser resolve different defaults and React reports a hydration
mismatch. Use `useFormatters()` (`date`, `dateTime`, `number`, `currency`,
`relative`), which carries the negotiated locale explicitly.

## Adding a locale

1. Add it to `LOCALES` in `packages/entifix/ts/i18n/src/locales.ts`.
2. Add `src/resources/<locale>/*.ts`, each annotated `typeof import('../es/…')`.
3. Add it to `resources` in `src/resources/index.ts`.
4. Seed `locale.supported` for each app in `apps/config-service/src/db.ts`.
5. `node tools/check-i18n.mjs`.

## The gates

| Gate                            | Catches                                                                                                                                                                                                         |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `react/jsx-no-literals`         | A string written into JSX children.                                                                                                                                                                             |
| i18next module augmentation     | A key that does not exist, in any consumer.                                                                                                                                                                     |
| `node tools/check-i18n.mjs`     | Key parity, empty values, placeholder drift across locales.                                                                                                                                                     |
| `pnpm nx test @r10c/i18n-check` | An error code a service emits with no entry in the `errors` catalog.                                                                                                                                            |
| `locale-switch.mock.spec.ts`    | A screen that was never wired to the provider.                                                                                                                                                                  |
| `r10c/no-foreign-app-namespace` | The `app` namespace bound outside `apps/`, through any binder — `useT`, `getServerT`, `getServerTFor`, `getServerTranslateKey`. A new binder must be added to that rule's `BINDERS` set or it escapes the gate. |

**What no gate catches:** copy inside a JSX expression —
`{saving ? 'Saving…' : 'Save'}` is an expression, not a child, and lint is blind
to it. Treat a string literal inside JSX braces with the same suspicion as one
outside them.

Design-system playground pages (`src/app/page.tsx`) are excluded on purpose: the
English there is the specimen being demonstrated.
